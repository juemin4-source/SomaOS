# SomaOS 1.0 — 北极星文档

> **状态:** 设计讨论产物，尚未锁定
> **日期:** 2026-07-25
> **前序:** GATE-001/002/002A 完成，治理链已验证
> **下文:** 本文件定义方向，不定义实现步骤

---

## 一、一句话北极星

> **把 AI 辅助研发从"一次性对话"升级为"有组织、可积累、可验证的研发能力体系"。**

当前 AI Coding Agent 的核心限制不是模型能力——模型已经能读代码、改文件、跑测试了——而是每次对话从零开始，没有工作记忆、阶段感知和能力复用。

SomaOS 1.0 解决的问题不是"AI 能不能写代码"，而是"AI 的研发工作如何像人的研发工作一样有结构、可管理、可改进"。

---

## 二、产品定位

### SomaOS 1.0 是

一个成熟、可靠的 Coding Agent。

用户输入研发任务，Soma 流式工作——读代码、执行命令、修改文件、运行测试、输出结果。用户可以随时打断、补充、纠正和继续。错误不会轻易破坏整个任务。会话和研发任务可以恢复。

### SomaOS 1.0 不是

- 通用 Agent 平台
- 分布式工作流引擎
- 企业权限系统
- 事件溯源产品
- 多租户云服务
- 自研 MCP/ACP 或模型协议
- 跨行业能力市场

### 聚焦领域

仅软件研发。不试图证明跨创作、设计或其他专业领域的通用性。

## 三、用户路径

1.0 必须通过三条核心路径的验证，但不要求同时交付。每条路径在真实使用中成熟后再进入 1.0 验收。

### 路径 A：调查与修复

```
用户陈述 Bug → Soma 理解问题 → 定位根因 → 提出修复方案
→ 执行修改 → 运行验证 → 产生 Evidence → 输出修复结论
```

当前状态：GATE-002 已验证治理链在此路径上对真实模型生效。
当前限制：仅限单文件、单行 Bug。需要扩展到多文件、多步骤修复。

### 路径 B：功能交付

```
需求 → 澄清 → 规格 → 计划 → 实施 → Review → QA → 交付
```

涉及最多的阶段转换和能力组合。1.0 的旗舰路径。

### 路径 C：项目接管

```
已有代码库 + 未完成任务 → 理解架构和状态
→ 读取 Review Findings → 修复失败测试
→ 继续未完成功能 → 输出增量交付
```

最能体现"AI 不是从零开始"的价值。与路径 B 共享大量能力（理解项目、恢复状态、处理 Findings）。

## 四、内部能力体系

SomaOS 的能力体系是分层的。用户看到的是简洁的 Coding Agent，后台是有组织的工作能力。

```
Skill ───── 对用户承担完整研发责任的能力产品（/review、/qa、/ship）
  │
Combo ───── 根据目标和中间结果动态装配的能力结构
  │
Softill ─── 可发现、可调用、可复用的研发能力单元（code.search@1、code.patch@1）
  │
Organ ───── AI 与真实软件环境的连接层（FileOrgan、ProcessOrgan、GitOrgan）
```

### Organ

物理连接层。当前的 FileOrgan、ProcessOrgan、GitOrgan 已验证可用。

### Softill

研发语义层面的能力单元，不是通用工具包装。每个 Softill 有明确的输入输出契约、副作用声明和证据产出。

示例：`code.search@1`、`file.read@1`、`code.patch@1`、`test.run@1`、`git.diff@1`。

Softill 与 Capability Contract 是同一事物的两层——Contract 是 Soma 内部治理的正式契约，Softill 是向 Combo 和 Skill 暴露的可调用接口。

### Combo

根据当前任务和中间结果动态形成的执行结构。不是固定 DAG。

Combo 的内部结构变化对用户透明，但用户可以在需要时查看"当前工作计划及其调整"（渐进式显露）。

### Skill

对用户承担完整研发责任的能力产品。Skill 可以使用多个 Combo，跨越多个阶段。

示例：`investigate`、`review`、`qa`、`ship`。用户可以通过自然语言或类似 `/review` 的方式调用。

## 五、研发工作体系

### 原则

> 有专业方法，但不被流程绑死；允许动态调整，但不让每次工作从零即兴。

### 阶段

研发阶段定义了 Soma 当前承担的研发责任，不是强制步骤：

| 阶段 | 解决的问题 | 进入条件 |
|------|-----------|---------|
| 调查 | 发生了什么？根因是什么？ | 收到 Bug 报告 |
| 澄清 | 到底要做什么？ | 模糊需求 |
| 规格 | 具体怎么做？边界是什么？ | 需求已理解 |
| 计划 | 先做什么后做什么？ | 规格已确定 |
| 实施 | 写代码。 | 方案已确定 |
| Review | 代码是否正确、合理？ | 实施完成 |
| QA | 功能是否真的工作？ | Review 通过 |
| 交付 | 用户是否验收？ | QA 通过 |

### 路由

任务类型只提供默认入口路线：

- **Bug 修复：** 调查 → 实施 → 验证
- **功能交付：** 澄清 → 规格 → 计划 → 实施 → Review → QA → 交付
- **项目接管：** 接管侦察 → 状态重建 → 判断当前阶段 → 继续工作

这些路线不是固定铁轨。Soma 可以根据实际情况从任意阶段进入、跳过已满足前提的阶段、插入 Review 或 QA、根据发现回退、在任务性质变化时切换路线。

### 阶段转换控制

- **Soma 自动处理：** 低风险、事实明确的转换
- **Review/QA：** 可以要求回退到实施或调查阶段
- **用户决定：** 涉及需求解释、范围扩大、方案改变和正式交付

用户也可以通过自然语言或 `/review`、`/qa`、`/ship` 等方式显式指定。

## 六、渐进式显露原则

SomaOS 的默认主界面是成熟、直接的 Coding Agent 交互。Softill、Combo、研发阶段与 Evidence 不应成为用户必须理解和操作的概念——它们是 Soma 的内部工作模型。

**默认可见（研发事实，非内部术语）：**

- 当前任务
- 当前工作状态或研发阶段
- 简短计划与下一步
- 正在执行的命令和能力
- 修改的文件
- 测试结果
- Review Findings
- 是否等待用户决定

**按需展开（用户询问时才显示）：**

- 为什么进入当前阶段
- 本次使用了哪些 Softill
- Combo 如何根据结果调整
- 哪些验证支持当前结论
- 为什么退回上一阶段
- 为什么某个操作被拒绝

**内部术语到用户概念的映射：**

| 内部概念 | 用户看到的 |
|---------|-----------|
| Combo | 当前工作计划及其调整 |
| Softill | 正在使用的研发能力 |
| Evidence | 测试、构建、Diff、复现结果 |
| 阶段系统 | 调查、规划、实施、审阅、验证、交付 |
| Policy | 权限请求或风险提示 |

**核心原则：**

> 内部高度结构化，外部保持自然；默认简单，细节可检查。

SomaOS 的差异化通过工作连续性、方法质量、完成度和能力复用体现，不通过向用户展示系统复杂度来证明存在。

---

## 七、差异化（与 Claude Code / Codex 的对比）

SomaOS 1.0 与现有 Coding Agent 的核心区别不在聊天界面，而在后台能力体系：

| 维度 | 现有 Coding Agent | SomaOS 1.0 |
|------|------------------|------------|
| 工作记忆 | 每次会话从零开始 | 有阶段感知和上下文延续 |
| 能力组织 | 平铺的 Tool 列表 | 分层的 Softill → Combo → Skill |
| 工作结构 | 无 | 可路由的研发阶段体系 |
| 方法质量 | 取决于当前 Prompt | 有内置的 Review、QA、交付流程 |
| 能力复用 | 无（每次重新描述） | Softill 可发现和复用 |
| 完成判定 | 模型自己声明 | Evidence + ClaimAdjudicator 系统验证 |
| 错误恢复 | 对话重试 | 回退到前一阶段 |

## 八、阶段 Gate 与版本哲学

### 核心区分

- **1.0 验收目标：** 最终要做到什么（三条路径全部可重复完成）
- **阶段 Gate：** 当前最大的不确定性是否被解决
- **版本号：** 有一批用户可感知、值得冻结的能力时再发

版本号不等于开发步骤。

### 四个大阶段

#### 阶段一：执行内核成立（0.2 接近完成）

已完成的：
- 模型调用（DeepSeek 链路已验证）
- 工具执行（File/Process/Git Organ）
- 基础 Capability（CapabilityContract + Registry）
- Policy / Evidence 实验（GATE-001/002）
- Runtime 边界（CLI → Client → Runtime 三层）

收尾标准：不再扩建通用 Runtime 基础设施。

#### 阶段二：研发能力原生化（下一阶段，版本号未定）

目标：把 Softill、Combo、Skill、研发阶段从概念变成实际运行能力。

做法：围绕一个真实场景（调查并修复 Bug）自然长出：

- 代码侦察 Softill
- 测试与修复 Softill
- 调查 Combo
- 修复 Combo
- 验证 Combo
- 必要的阶段转换

验收：这套东西能在日常开发中真实使用。

#### 阶段三：完整研发主链

在 Bug 修复稳定后，扩展到澄清 → 规格 → 计划 → 实施 → Review → QA → 交付的全链路，同时支持项目接管。

"项目接管"和"功能交付"不机械拆成两个独立版本——它们共享大量能力，哪个先在真实使用中出现就先做哪个。

#### 阶段四：1.0 — 整体达到日用水平

三条路径全部可重复完成，且满足：
- 聊天体验足够成熟
- Softill 真能复用
- Combo 真会根据结果调整
- 阶段体系不是死流程
- 任务可以恢复
- 你愿意拿它长期开发自己的项目

## 九、范围控制规则

每当提出新底层系统时，必须回答：

1. 它直接支撑哪条 1.0 用户路径（A/B/C）？
2. 不建设它会具体阻断什么？
3. 有没有更简单的替代方案？

不符合这三条的底层系统，不进 SomaOS 1.0。

## 十、当前 immediate next

阶段二（研发能力原生化）的第一批 Softill 和 Combo 不应由我们坐在桌前设计出来。

**能力和供体是 gstack。** gstack 已经在真实研发中长出了完整的 Skill 体系（`/review`、`/qa`、`/ship` 等）、阶段路由和交付纪律。SomaOS 的第一套研发能力应该从 gstack 的源码和真实运行轨迹中解剖出来，而不是从头发明。

因此 immediate next 不是编码，而是：

> **GATE-SOMA-GSTACK-EXTRACTION-001 — gstack 能力考古与原生化**

一个四阶段的提取 Gate：

1. **源码地图** — 扫描 gstack，建立命令/Skill、入口路由、Prompt 规则、脚本工具、产物格式、上下文传递、Review/QA Gate 的全景图
2. **责任分解** — 对每个主要 Skill 回答：用户交给它什么责任？它必须产出什么？内部有哪些稳定动作？
3. **四层候选表** — 输出 Skill、Combo、Softill、Stage/Routing 四张候选清单，每个标记来源、职责、输入输出、复用位置、动态性
4. **纵向切片** — 选第一刀（候选：Review Finding 处理），抽取并原生化第一批能力

### Native 标准

某项能力成为 SomaOS 原生能力，不取决于它是否用 Rust 重写，而取决于：

- Soma 能发现它
- Soma 理解它的责任与输入输出
- Soma 能在合适阶段选择它
- 它能调用 Softill 或子 Combo
- 它的状态与产物属于 Soma 工作对象
- 它能根据反馈调整
- 它不依赖用户手动复制 Prompt 才能运行

即使第一版内部仍通过 Claude Code/gstack 执行，只要控制权、工作状态和能力语义已经进入 Soma，它也可以算"Hosted Native"。

### 双层关系

```
Claude Code → gstack（Hosted 能力体系，继续运转）
                ↓ 能力考古与抽取
             SomaOS（逐步吸收 Native 能力）
```

gstack 继续帮助开发 SomaOS。每吸收一块，SomaOS 就少依赖一点外部 Prompt 编排，多拥有一点原生研发能力。到 1.0 时 gstack 可能仍然作为能力来源、对照组或兼容层保留。
